Work Term Objectives

Learning Goals

Going into my second work term at Brock Solutions, I wanted goals that pushed beyond basic familiarity with the team's tools and processes. After Winter 2026, I already had a starting point in the SmartBag Reconciliation codebase. For Summer 2026, I focused on writing code that fit existing patterns more cleanly, reviewing others' work more carefully, communicating earlier on design decisions, using AI more effectively, and managing time-sensitive issues with clearer time boxes.

The goals I set for the term were as follows:

  1. Write code that more closely matches existing patterns and preferences in the codebase. I planned to use AI and other tools to study those patterns, keep changes aligned with single responsibility and clean separation of concerns, and look at previous pull requests and change logs as references. Success would mean new work fitting into the existing structure more easily, so later features are simpler to add and responsibilities are easier to find.
  2. Improve at reviewing code and asking good questions about it. I planned to take more initiative on pull requests assigned to my team, checking whether changes followed local practices and were clear and readable, and leaving comments when something felt unclear or could be improved. Doing that regularly should also improve how I write my own code, because I would start judging my changes against patterns I had seen elsewhere.
  3. Become more proactive about asking questions and communicating with teammates when early design decisions are uncertain. During my previous term there were cases where I made structural changes that did not ultimately resolve functionality, and that rework could have been avoided with earlier advice. Success for this goal meant reaching out sooner so the structure of what I was building stayed sound and left room for later additions.
  4. Use AI more efficiently both when writing code and when investigating the existing codebase. For features, I wanted AI to help surface patterns and produce drafts or proofs of concept that I could then review carefully. For bugs, I wanted it to help with early investigation, such as identifying likely starting points or expected behaviour from tests, without letting generated output replace my own validation. The aim was to spend less time on the first pass-through and more time refining a structurally sound solution.
  5. Improve at time-boxing and escalating earlier on time-sensitive issues. When working on a critical bug or similarly urgent item, I planned to set a clear progress target for a short window—perhaps an hour or two—and reach out if I was not on track. The intent was to keep those issues moving toward a timely fix and reduce friction for both the team and my own workday.

Why I picked these goals

These goals all support the broader theme of becoming more independent in a production environment. Matching patterns and reviewing code carefully help me contribute changes that fit the team's standards. Asking questions earlier and time-boxing time-sensitive work help me avoid getting stuck or creating rework. Using AI thoughtfully sits in the middle: it can speed up investigation and drafting, but only if I still take responsibility for evaluating the result. Together, they were meant to turn the familiarity I built in Winter 2026 into stronger judgment and ownership in Summer 2026.
