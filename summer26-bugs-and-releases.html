Bugs, Releases, and Production Discipline

Alongside larger features, a substantial part of this work term involved smaller changes and bug work in the context of SmartSuite's release process. SmartSuite has monthly releases, plus occasional hot fixes. Ahead of a release, bugs are tagged as planned for that release, for example Planned24.xx.0. Staying on top of those cycles, and being proactive with time-sensitive high-priority bugs, was one of the biggest challenges of the term.

What This Covered in My Role

  • Tracking and prioritizing bugs planned for upcoming monthly releases.
  • Participating in regression cycles and documenting results.
  • Handling time-sensitive, high-priority bugs as release dates approached.
  • Applying production-safe habits such as feature toggles, careful shared-code changes, and API/client compatibility awareness.

Monthly Releases and Planned Bugs

Each release cycle includes a board of bugs planned for that version. Querying by tags such as Planned24.16.0 or Planned24.17.0 made it possible to see what needed to land before the release, and to prioritize work accordingly. Some bugs were also tagged as regression-related, which helped separate ongoing backlog items from issues found during the release testing window.

Querying bugs planned for a specific monthly release using the Planned24.16.0 tag.

Regression Cycles

Each release also has a regression cycle: a period that typically lasts a few days where developers and QA on the team pause feature work and run regression tests. Those tests are selected based on the features included in the release. The team evaluates which functionality, areas of the app, and modules were touched by the changes and therefore pose a higher risk of regression.

Sometimes high-priority regression bugs are identified during that window and must be addressed before release. That creates a short, high-pressure period where communication, prioritization, and careful testing matter as much as the fix itself.

Tracking Open Bugs

Outside the narrow regression window, I also spent time tracking open bugs for the Reconciliation team area, reviewing severity and priority, and identifying which items were already planned for upcoming releases. That habit made it easier to jump between feature work and release support without losing track of what was time-sensitive.

Open bugs for the Reconciliation area, including planned-release and regression tags.

Lessons from a Large Production Codebase

Working in SmartSuite also reinforced several lessons about making changes safely in a large, monolithic, production codebase:

  • Decide carefully when it is safe to touch an existing piece of functionality versus when it is safer to create a new function. Changing shared code can have broad effects, especially when multiple teams and customers rely on the same paths.
  • Use temporary feature toggles when needed. For the grouping recovery feature, I had to make sure that the smaller changes I landed early were not effectively shipping part of the feature before it was ready. At Brock we work out of the live release / 24.0 branch, so changes have to be evaluated in terms of customer impact. Because some of the grouping work went into a release before the one it was designated for, I needed to keep those changes non-functional until the feature was meant to be enabled.
  • Consider compatibility between newer API versions and older clients. Some customers run older client solutions against newer APIs, so removing fields from DTOs or removing endpoints cannot be done carelessly.
